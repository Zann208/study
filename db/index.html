0 Start here: the big picture
In one lineA database is an organised, shared store of facts, and the DBMS is the program that looks after it for you.

Think of a school library. It has members, books, and a record of who borrowed what. You could keep all of that in one spreadsheet, but it breaks down fast: two librarians edit the same row at once, someone types a member number that does not exist, a power cut loses half an edit, and anyone who opens the file can change everything.

A DBMS (database management system) solves exactly those problems. It stores the data, checks your rules every time something changes, lets many people work at the same time safely, finds things quickly even in millions of rows, and controls who is allowed to do what.

1 Databases and the relational model
In one lineIn a relational database, everything is stored in tables, and tables are linked by matching values.

A table (formal name: relation) is a grid. Each row (tuple) is one thing, such as one member. Each column (attribute) is one property of that thing, such as the member's name. The set of values a column is allowed to hold is its domain, for example "whole numbers" or "dates".

MemberIDNamePhone
1Ana081-111
2BenNULL
3Chai089-333

Blueprint vs contents

The schema is the blueprint: the table's name and its columns, Member(MemberID, Name, Phone). It rarely changes. The state is the rows that are inside the table right now. It changes every time someone adds, edits or deletes a row. The order of the rows does not matter: shuffle them and it is still the same table.

Keys: telling rows apart

  • A superkey is any set of columns whose values are never repeated, so it always picks out exactly one row. {MemberID, Name} is a superkey.
  • A candidate key is a superkey with nothing extra in it: remove any column and it stops being unique. {MemberID} is one.
  • The primary key (PK) is the candidate key you choose as the official ID. It may not be NULL.
  • A foreign key (FK) is a column in one table that holds a key value from another table. Loan.MemberID points at Member.MemberID. That pointing is how tables are linked.

NULL means "no value here"

Ben's phone is NULL. That could mean the phone number is unknown, that he has no phone (does not apply), or that it simply has not been entered yet. NULL is not zero and not an empty string.

The three rules the DBMS guards

RulePlain meaning
Key constraintNo two rows may share the same key value.
Entity integrityA primary key value can never be NULL.
Referential integrityA foreign key must point at a row that really exists, or be NULL.

Remember
  • Table = relation, row = tuple, column = attribute.
  • A primary key identifies each row and is never NULL.
  • A foreign key points at another table's key, and may be NULL.
From the course materials

Definitions

  • A database is a collection of related data.
  • Data are known facts that can be recorded and have implicit meaning.
  • A database represents some aspect of the real world, called the miniworld or universe of discourse (UoD).
  • A DBMS (database management system) is a general-purpose software system that facilitates the process of defining, constructing, manipulating and sharing databases among various users and applications.
  • An application program accesses the database by sending queries or requests for data to the DBMS.
  • A query typically causes some data to be retrieved; a transaction may cause some data to be read and some data to be written into the database.

Relation schema and relation state

A relation state r(R) is a subset of dom(A1) × dom(A2) × … × dom(An), where A1 … An are the attributes. For an Enrollment relation with attributes Student_number, CourseID and Grade, r(Enrollment) ⊆ dom(Student_number) × dom(CourseID) × dom(Grade): each tuple (row) is one possible combination drawn from those domains, and r(Enrollment) is one possible state of the Enrollment relation.

WordMeans
SchemaThe relation name and its attributes (the column headings)
AttributeA column
TupleA row
StateThe set of tuples in the relation at one moment

Five statements to be able to illustrate

  • Tuples in a relation do not have any particular order. Any order of the rows is the same relation.
  • NULL can have several meanings. The worksheet example inserts a student whose Plan is NULL: the value may be unknown, not applicable, or not yet available.
  • Keys are always superkeys. A superkey is any set of attributes that uniquely identifies a tuple. A candidate key is a minimal superkey: no proper subset of it still identifies a tuple uniquely.
  • A foreign-key value in a tuple can be NULL. A foreign key (FK) is a link between the attributes of one table and the primary key of another; FK values are allowed to be NULL.
  • The delete operation can violate only referential integrity, not key constraints nor entity integrity. Past paper Q2.5 — no worked answer in the materials

Joining on a primary key / foreign key

Joining Course (primary key Code) with Enrollment (foreign key CourseID) returns as many rows as there are foreign-key values in the field being joined: eight Enrollment rows give eight result rows.

2 SQL DDL: tables, constraints and referential actions
In one lineDDL is the part of SQL that builds the empty tables and writes the rules the data must follow.

SQL is the language you type to talk to a relational DBMS. Its commands fall into families:

FamilyStands forWhat it doesCommands
DDLData Definition LanguageBuilds and changes structureCREATE ALTER DROP
DMLData Manipulation LanguageReads and changes rowsSELECT INSERT UPDATE DELETE
DCLData Control LanguageGives and removes permissionsGRANT REVOKE
TCLTransaction Control LanguageSaves or undoes a group of changesCOMMIT ROLLBACK

A table with rules

CREATE TABLE Member (
    MemberID INT PRIMARY KEY,          -- the official ID
    Name     VARCHAR(50) NOT NULL,     -- must be filled in
    Phone    VARCHAR(15) UNIQUE,       -- no two members share a phone
    Age      INT CHECK (Age >= 7),     -- any rule you can write as a condition
    Status   VARCHAR(10) DEFAULT 'active'   -- used when nothing is given
);

Every rule after a column is a constraint. Once it is written, the DBMS refuses any change that would break it. You do not have to remember to check; the database checks for you.

Linking two tables

CREATE TABLE Loan (
    LoanID   INT PRIMARY KEY,
    MemberID INT,
    FOREIGN KEY (MemberID) REFERENCES Member(MemberID)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

What happens to the loans when a member changes?

The words after ON DELETE and ON UPDATE are referential actions. They answer: "if the member row is deleted, or its ID changes, what should happen to the loan rows that point at it?"

ActionThink of it asResult for the loan rows
CASCADEFollow the parentDeleted too, or their MemberID changes to the new value
SET NULLUnlinkMemberID becomes NULL
SET DEFAULTRe-link to a fallbackMemberID becomes the column's DEFAULT value
RESTRICT / NO ACTIONRefuseThe delete or update of the member is rejected; nothing changes

If you write no action, MySQL uses NO ACTION, which in MySQL behaves the same as RESTRICT.

Referential actions

The action after ON DELETE or ON UPDATE says what happens to the referencing rows when the referenced row is deleted or its key changes.

  • SET DEFAULT — the lab's assignment table keeps its row and falls back to the reserved teacher: TeacherID INT DEFAULT 1 … ON DELETE SET DEFAULT.
  • SET NULL — the worksheet's answer for "when a course instructor is removed, the corresponding AdvisorID should be set to NULL".
  • CASCADE — the worksheet's answer for "if the instructor's name is updated, the change should cascade to the Student table".
ALTER TABLE Student
ADD AdvisorID VARCHAR(255) NOT NULL;

ALTER TABLE Student
ADD CONSTRAINT FK_Advisor
FOREIGN KEY (AdvisorID) REFERENCES Course(Instructor)
ON UPDATE CASCADE
ON DELETE SET NULL;
Will MySQL accept this?Not as written. MySQL rejects SET NULL on a column declared NOT NULL, so the worksheet's AdvisorID … NOT NULL with ON DELETE SET NULL fails; drop the NOT NULL. MySQL also requires the referenced column to be indexed, ideally the parent's primary key. The DDL lab's ON DELETE SET DEFAULT is standard SQL, but MySQL's InnoDB engine rejects it; it runs on systems such as PostgreSQL. 3 ER modelling: entities, cardinality and participation
In one lineAn ER diagram is a drawing of your data, made before you build any tables.

Before writing CREATE TABLE, you sketch what the system needs to remember. ER stands for Entity–Relationship.

PieceShapeMeaningLibrary example
Entity typeRectangleA kind of thing you storeMember, Book
AttributeOvalA property of that thingName, Title
Key attributeOval, name underlinedThe property that identifies each oneMemberID
Multivalued attributeDouble ovalCan hold several values for one thingA member's phone numbers
Relationship typeDiamondHow things are connectedMember borrows Book

Cardinality: how many?

On each side of a diamond you write 1, N or M.

  • 1 : 1 — one on each side. One member has one library card.
  • 1 : N — one on one side, many on the other. One branch holds many books; each book is in one branch.
  • M : N — many on both sides. A member borrows many books, and a book is borrowed by many members over time.

Participation: must or may?

A double line from an entity to the diamond means total participation: every one of them must take part. A single line means partial: some may not. Every loan must belong to a member (total), but a member does not have to have borrowed anything (partial).

Attributes on a relationship

Some facts belong to the link, not to either thing. The due date is not a property of the member or of the book; it is a property of one borrowing. So DueDate hangs off the borrows diamond.

Words to know

ER modelERDEntity typeKey attributeMultivalued attributeRelationship typeCardinality ratio1 : NM : NTotal participationPartial participationWeak entity
Remember
  • Rectangle = entity type, oval = attribute, diamond = relationship.
  • 1:1, 1:N, M:N say how many; double line = must, single line = may.
  • A fact about the link itself goes on the diamond.

Reading the notation

  • Rectangles are entity types; ovals are attributes; the key attribute is underlined; diamonds are relationship types.
  • A double-outlined attribute oval marks a multivalued attribute (the inventory diagram's Price_change, which holds the price history with Price and Datetime).
  • Attributes can also hang off a relationship (Supply carries Qty, Amount and RemainQty; "in" carries Qty and Amount).
  • Cardinality ratio is written at each end of the relationship: 1, N or M.
  • Participation: a double line means total participation (every instance must take part); a single line means partial.

Inventory: how the constraints were justified

RelationshipCardinalityParticipation

Vote: the same ideas on a legislative database

  • STATE (Name, Region) — have — CONGRESS_PERSON: a congressperson must represent exactly one state (1 : N, total on the congressperson side); a state can have many congresspersons.
  • CONGRESS_PERSON — sponsored — BILL: a bill can be sponsored by M persons (M : N).
  • CONGRESS_PERSON — voted — BILL with attribute Result: each congressperson can vote for N bills (M : N).
  • Enumerated domains appear in the requirements, not the diagram: Region, Party, Passed_or_failed and Vote each have a fixed set of values.

4 Relational algebra
In one lineRelational algebra is a small set of operations that take tables in and give a table out, so they can be chained into a question.

Before learning SQL syntax, it helps to see the handful of moves every query is built from. Because each move returns a table, the result of one can be fed straight into the next, like steps in a recipe. It is called procedural because you spell out the steps.

Select σ

Selects tuples (horizontally) that satisfy a condition: σ<condition>(Relation). Comparison operators =, ≠, <, ≤, >, ≥; connectives AND (∧), OR (∨), NOT (¬).

Project π

Returns the values of certain attributes (vertically), leaves the others out, and eliminates duplicate rows: πattr1, attr2, …(Relation).

π ID, Name, Salary (INSTRUCTOR)

Union and join

Union is a binary operator on two relations that removes duplicates. Join combines two tables on a condition: (Relation1) ⋈condition (Relation2). Joining on equality of attributes is an equijoin.

5 Intermediate SQL
In one lineSQL is the language you actually type to ask questions; every SELECT is a recipe made of a few clauses.

The shape of a question

SELECT   m.Name, COUNT(*) AS Loans     -- 5. which columns to show
FROM     Member m                       -- 1. start from these tables
JOIN     Loan l ON l.MemberID = m.MemberID
WHERE    l.DueDate >= '2026-01-01'      -- 2. throw away rows you do not want
GROUP BY m.Name                         -- 3. put the remaining rows into buckets
HAVING   COUNT(*) > 2                   -- 4. throw away buckets you do not want
ORDER BY Loans DESC                     -- 6. sort the result
LIMIT    5;                             -- 7. keep only the first few

You write the clauses in the order SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. The DBMS thinks in the order shown by the numbers: it needs the tables first, then filters rows, groups them, filters groups, and only then picks the columns to show.

WHERE or HAVING?

Ask: "can I test this on one row by itself?" If yes, it goes in WHERE (DueDate >= …). If it needs a whole group to answer (COUNT(*) > 2), it goes in HAVING.

Window functions

COUNT(*) OVER (PARTITION BY MemberID) also counts per group, but unlike GROUP BY it keeps every row and writes the group's count beside each one.

6 Datalog and recursive queries
In one lineDatalog writes a query as rules of the form "this is true if all of that is true".

A rule has a head on the left and a body on the right of the arrow. The head is a result row; it is produced whenever every condition in the body can be matched.

late(n) <- Member(m, n, _) AND Loan(_, m, _, d) AND d < '2026-01-01'
  • Read it as: "n is in late if there is a member with ID m and name n, and a loan for member m with due date d, and d is before 1 January 2026."
  • Columns are matched by position, not by name. Member(m, n, _) means first column m, second column n.
  • _ means "there is a value here but I do not care what it is".
  • Using the same letter twice (m in Member and in Loan) means the values must be equal. That is how Datalog joins.

Safe rules

A rule is safe when every variable in the head, and every variable used in a NOT or in a comparison, also appears in a normal (non-negated) table in the body. If a variable is not tied to a real table, it could stand for any value at all, and the answer would be infinite.

Recursion

A rule may use its own name in its body. That lets you follow a chain of any length: a category, its parent, the parent's parent, and so on. SQL does the same with WITH RECURSIVE: a base case gives the starting rows, a recursive case adds the next step from the rows found so far, and it repeats until no new rows appear.

The safety rule is standard Datalog theory; the course materials ask why three rules are unsafe but do not include the answer.

Datalog rules

A rule has a head and a body: ans(x, y) <- R(x, y, z) AND z > 20.0. Underscores are attributes that are matched but not used. Translating a rule means producing (1) relational algebra, (2) SQL and (3) an English sentence.

ans(x,y) <- WORKS_ON(x,y,z) AND z > 20.0        -- WORKS_ON(Essn, Pno, Hours)

(1) π Essn, Pno (σ Hours > 20.0 (WORKS_ON))
(2) SELECT Essn, Pno FROM WORKS_ON WHERE Hours > 20.0;
(3) Display Essn and project number where the working hours are greater than 20.

Recursive CTE (WITH RECURSIVE)

WITH RECURSIVE parents AS (
  SELECT id, name, parent_id, 0 AS relative_depth        -- base case
  FROM categories
  WHERE name = 'Grandchild A1b'
  UNION ALL
  SELECT cat.id, cat.name, cat.parent_id, p.relative_depth - 1   -- recursive case

7 File organization and indexing calculations
In one lineData sits on disk in fixed-size blocks, reading a block is the slow part, and an index exists to read fewer blocks.

The disk does not hand over one row at a time. It reads a whole block (also called a page), for example 512 or 4096 bytes. Reading a block takes far longer than any calculation done on it, so the cost of a search is measured in block accesses.

Fitting rows into blocks

SymbolMeaningExample
RRecord size: add up every field's size100 bytes
BBlock size1024 bytes
bfrBlocking factor: whole records per block = floor(B / R)floor(1024/100) = 10
rNumber of records5,000
bNumber of blocks = ceiling(r / bfr)ceiling(5000/10) = 500

Round down for bfr because half a record does not fit. Round up for b because a half-full last block is still a block.

Finding a record without an index

  • Linear search: read blocks one by one. On average you read half of them (250 here).
  • Binary search: only possible if the file is sorted on what you are looking for. Halve the range each time: about log2(500) ≈ 9 reads.

What an index is

It works like the index at the back of a textbook: a short, sorted list of (key, page number). In a database each index entry is (key value, pointer), and the pointer says where the block or record is. Entries are much smaller than full records, so the index fits in far fewer blocks and is quick to search.

IndexBuilt onEntries
Primary indexThe field the file is sorted by (a key)One per block (sparse)
Secondary indexAny other fieldOne per record (dense)

Multilevel index: an index of the index

If the index itself is many blocks long, build a small index on top of it, then another on top of that, until the top level fits in one block. To find a record you read one block per level, then the data block: levels + 1 block accesses. That idea is the basis of the B-trees real databases use.

8 Heuristic query optimization
In one lineYou say what answer you want; the DBMS works out the cheapest order of steps to get it.

SQL is declarative: it describes the result, not the method. The same question can be computed in many orders, and some orders are thousands of times slower. The part of the DBMS that picks the order is the query optimizer.

Query trees

A query can be drawn as a tree. The tables are the leaves at the bottom, each operation (σ, π, ⋈, ×) is a node, and data flows upward to the answer at the top. Rewriting the tree changes the steps without changing the answer.

The rules of thumb (heuristics)

  1. Split a filter with many ANDs into separate small filters, so each can move on its own.
  2. Filter early: move each filter down the tree to sit right above the table it tests. Fewer rows go up.
  3. Join, do not pair everything: a Cartesian product followed by a matching condition is replaced by a join.
  4. Carry only what you need: keep just the columns used later (join keys and the output) as low as possible.

Why it matters

Pair 1,000 members with 50,000 loans and you get 50 million combinations before filtering. Filter the members to the 20 you want first, then join, and the work is tiny. Same answer, very different cost.

Words to know

Query optimizerDeclarative languageQuery treeHeuristicCascade of selectionsSelection push-downProjection push-downJoin orderCost-based optimization
Remember
  • You say what you want; the optimizer decides how.
  • Filter early, join instead of pairing everything, carry only needed columns.
From the course materials

A query is first written as a query tree: Cartesian products of the base relations at the bottom, one big selection of the whole WHERE clause above them, and the projection at the top. Heuristic optimization rewrites that tree into an equivalent one that is cheaper to execute.

The four steps shown in the slides

  1. Cascade selection — split the single conjunctive σ into one σ per condition.
  2. Move selection down — push each σ as far down the tree as possible, next to the relation it restricts (e.g. σProdType = 'Widget' directly over Product, σDate.Month = July directly over Invoice).
  3. Cartesian product with select becomes join — a × followed by a σ on a join condition is replaced by ⋈ with that condition.
  4. Projection push-down — add π nodes low in the tree so that only the attributes needed later (join keys and output columns) travel upward; e.g. πInvID, CustID over Invoice, πID, Type over Customer.
π Type (σ ProdType = 'Widget' (σ Date.Month = July (Customer ⋈ Invoice ⋈ LineItem ⋈ Product)))

9 Transactions, commit and rollback
In one lineA transaction is a group of changes that must all happen, or none of them.

Moving 100 from account A to account B is two changes: take 100 from A, add 100 to B. If the system crashes between them, money disappears. Wrapping both in a transaction makes them one unit.

START TRANSACTION;
UPDATE Account SET Balance = Balance - 100 WHERE ID = 'A';
UPDATE Account SET Balance = Balance + 100 WHERE ID = 'B';
COMMIT;          -- make both changes permanent
-- or ROLLBACK;  -- undo both as if nothing happened

Two people at once

  • Inside your transaction you see your own changes straight away, even before COMMIT.
  • Other sessions do not see them until you COMMIT. They keep seeing the last saved value.
  • While you are changing a row you hold a lock on it. Anyone else who tries to change that same row has to wait until you COMMIT or ROLLBACK.
  • If a transaction is never finished, the DBMS normally rolls it back (for example when the connection closes).

ACID: the four promises

LetterPropertyPlain meaning
AAtomicityAll or nothing
CConsistencyRules hold before and after
IIsolationOthers do not see your half-finished work
DDurabilityOnce committed, it survives a crash

ACID and isolation levels are standard database theory; the course materials for this topic contain only the two-session lab.

Words to know

TransactionSTART TRANSACTIONCOMMITROLLBACKAutocommitSessionUncommitted changeLockLock waitACIDIsolation level
Remember
  • A transaction is all or nothing: COMMIT saves, ROLLBACK undoes.
  • You see your own uncommitted changes; others do not.
  • Changing a row locks it; others wanting to change it must wait.
From the course materials

The lab runs two sessions (connections A and B) against bank accounts 10001–10003 and asks what each session sees after each numbered query.

  • A session sees its own uncommitted changes inside the same transaction: after A debits 100, A reads the decreased balance.
  • Another session does not see uncommitted changes (default isolation behaviour): B still reads the original balance.
  • While A holds a lock on the row, B's withdrawal and transfer cannot complete; they wait on A's uncommitted transaction.
  • After A executes COMMIT, the change is permanent and B's transfer completes.
  • After A executes ROLLBACK, all of A's changes are discarded (account 10003 is back to 1000).
  • A transaction that is begun and neither committed nor rolled back is, in most DBMSs, rolled back automatically; until then other sessions do not see its changes.

10 Users, privileges and roles (MySQL)
In one lineEvery account gets only the permissions it needs, given with GRANT and taken back with REVOKE.

A database is shared, so it must decide who can read and who can change. In MySQL an account is a user name plus the host it connects from: 'ana'@'localhost' is a different account from 'ana'@'%', where % means any host.

Privileges and where they apply

LevelWritten asCovers
Global*.*Every database on the server
Databaselibrary.*Every table in one database
Tablelibrary.LoanOne table
ColumnSELECT (Name) ON library.MemberOnly some columns of one table
CREATE USER 'desk'@'localhost' IDENTIFIED BY '…';
GRANT SELECT, INSERT ON library.Loan TO 'desk'@'localhost';
REVOKE INSERT ON library.Loan FROM 'desk'@'localhost';

Roles: permissions in a bundle

Instead of granting the same five privileges to twenty librarians one by one, create a role, grant the privileges to the role once, and grant the role to each person. Change the role and everyone who holds it changes too.

CREATE ROLE 'librarian';
GRANT SELECT, INSERT, UPDATE ON library.* TO 'librarian';
GRANT 'librarian' TO 'ana'@'localhost', 'ben'@'localhost';

In MySQL 8, a granted role is not switched on automatically: the user runs SET ROLE, or an administrator sets it with SET DEFAULT ROLE.

Least privilege

Give each account the smallest set of permissions, from the narrowest set of hosts, that still lets it do its job. If it is ever misused, the damage is limited.

Q6 · 20 Index calculation, B = 1024

    
Block 1024 bytes, block pointer 6, record pointer 7, 30,000 fixed-length records with NAME 30, SSN 9, DEPARTMENTCODE 9, ADDRESS 40, PHONE 9, BIRTHDATE 8, SEX 1, JOBCODE 4, SALARY 4. File ordered by the non-key DEPARTMENTCODE; build a secondary index on SSN whose pointers point to the record level.

    
Asked: (1) bfr and number of blocks (unspanned); (2) first-level bfri; (3) first-level entries and blocks; (4) levels and total blocks of a multilevel index; (5) block accesses to reach a record via the multilevel index.

    
R = 30+9+9+40+9+8+1+4+4 = 114 bytes → bfr = floor(1024/114) = 8 → b = ceiling(30,000/8) = 3,750 blocks
entry = 9 + 7 (record pointer) = 16 bytes → bfri = floor(1024/16) = 64
secondary index is dense: r1 = 30,000 entries → b1 = ceiling(30,000/64) = 469 blocks
level 2: ceiling(469/64) = 8 blocks; level 3: ceiling(8/64) = 1 block → t = 3 levels, 469 + 8 + 1 = 478 blocks
accesses = t + 1 = 4

    
The numbers above apply the answer-sheet method (Topic 7) to the paper's values; they are not from a marked answer. Check them against the formulas before relying on them.

T7 Index formulas

    

      
R = Σ field sizes · bfr = floor(B/R) · b = ceiling(r/bfr) · left-over = B − bfr·R
Ri = key + pointer · bfri = fo = floor(B/Ri) · bi = ceiling(ri/bfri)
primary (file ordered by key): ri = b · secondary / dense: ri = r
linear: 1 / b / b÷2 · binary: ceiling(log2 b) · index search: ceiling(log2 bi) + 1
multilevel: t = ceiling(logfo r1) · accesses = t + 1 · blocks = b1 + b2 + … + 1

      
Block pointer when the index points at blocks; record pointer when it points at records.

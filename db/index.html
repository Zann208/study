0 Start here: the big picture
In one lineA database is an organised, shared store of facts, and the DBMS is the program that looks after it for you.

Think of a school library. It has members, books, and a record of who borrowed what. You could keep all of that in one spreadsheet, but it breaks down fast: two librarians edit the same row at once, someone types a member number that does not exist, a power cut loses half an edit, and anyone who opens the file can change everything.

A DBMS (database management system) solves exactly those problems. It stores the data, checks your rules every time something changes, lets many people work at the same time safely, finds things quickly even in millions of rows, and controls who is allowed to do what.

1 Databases and the relational model
In one lineIn a relational database, everything is stored in tables, and tables are linked by matching values.

A table (formal name: relation) is a grid. Each row (tuple) is one thing, such as one member. Each column (attribute) is one property of that thing, such as the member's name. The set of values a column is allowed to hold is its domain, for example "whole numbers" or "dates".

Blueprint vs contents

The schema is the blueprint: the table's name and its columns, Member(MemberID, Name, Phone). It rarely changes. The state is the rows that are inside the table right now. It changes every time someone adds, edits or deletes a row. The order of the rows does not matter: shuffle them and it is still the same table.

Keys: telling rows apart

  • A superkey is any set of columns whose values are never repeated, so it always picks out exactly one row. {MemberID, Name} is a superkey.
  • A candidate key is a superkey with nothing extra in it: remove any column and it stops being unique. {MemberID} is one.
  • The primary key (PK) is the candidate key you choose as the official ID. It may not be NULL.
  • A foreign key (FK) is a column in one table that holds a key value from another table. Loan.MemberID points at Member.MemberID. That pointing is how tables are linked.

Unique today is not enough

Right now no two members share a name, so {Name} looks unique. It is still not a key: tomorrow a second Ana can join. A key is a rule that must hold for every set of rows the table could ever contain, not only for the rows in it today.

A table can have more than one candidate key

A motorbike can be identified by its number plate (province, digits and letters together) and also by its engine number. Both are candidate keys. You pick one as the primary key; the other stays unique and is called an alternate key.

NULL means "no value here"

Ben's phone is NULL. That could mean the phone number is unknown, that he has no phone (does not apply), or that it simply has not been entered yet. NULL is not zero and not an empty string.

Details

Definitions

  • A database is a collection of related data.
  • Data are known facts that can be recorded and have implicit meaning.
  • A database represents some aspect of the real world, called the miniworld or universe of discourse (UoD).
  • A DBMS (database management system) is a general-purpose software system that facilitates the process of defining, constructing, manipulating and sharing databases among various users and applications.
  • An application program accesses the database by sending queries or requests for data to the DBMS.
  • A query typically causes some data to be retrieved; a transaction may cause some data to be read and some data to be written into the database.

Design stages

  1. Requirements collection and analysis: write down what the users need, both the data and the operations.
  2. Conceptual design: a high-level description of the data, usually an ER or UML diagram. It does not depend on any DBMS.
  3. Logical design (data model mapping): turn the conceptual design into the data model of a real DBMS, for example relation schemas.
  4. Physical design: choose storage structures, indexes and access paths.

After design: implement, populate with data, then maintain.

Database schema

The description of a database is its schema. It is specified during design and is not expected to change often. A schema diagram shows each relation with its attributes, for example STUDENT(Name, Student_number, Class, Major) and COURSE(Course_name, Course_number, Credit_hours, Department).

Origin of the relational model

Introduced by Edgar F. Codd of IBM Research in 1970 and based on the mathematical relation. Commercial systems followed in the early 1980s (IBM SQL/DS, Oracle); open-source systems such as MySQL, MariaDB and PostgreSQL came later.

Relation schema and relation state

A relation state r(R) is a subset of dom(A1) × dom(A2) × … × dom(An), where A1 … An are the attributes. For an Enrollment relation with attributes Student_number, CourseID and Grade, r(Enrollment) ⊆ dom(Student_number) × dom(CourseID) × dom(Grade): each tuple (row) is one possible combination drawn from those domains, and r(Enrollment) is one possible state of the Enrollment relation.

Domain and data type

The domain says what a value means; the data type says how it is written. In STUDENT(Name, Ssn, Home_phone, Address, Office_phone, Age, Gpa), the domain of Ssn is the set of valid nine-digit Social Security numbers, and its data type is a character string of the form ddd-dd-dddd.

Characteristics of relations

  • Degree. A relation with n attributes has degree n. STUDENT above has degree 7.
  • Subset of a Cartesian product. With dom(A1) = {1, 2, 3, 4}, dom(A2) = {John, Jack, Jessica} and dom(A3) = {M, F, N/A}, the product holds 4 × 3 × 3 = 36 possible tuples. A relation state is any subset of them, for example {(1, John, M), (2, Jessica, F)}.
  • Order of tuples. A relation is a set, so its tuples have no order.
  • Order within a tuple. Under the usual definition a tuple is an ordered list of values, so the values follow the attribute order of the schema. If a tuple is defined as a set of (attribute, value) pairs instead, that order no longer matters.
  • Atomic values. Each value is a single value; no lists or nested values in one cell.
  • NULL. Marks a value that is unknown or does not apply. Some students have NULL Office_phone because they have no office.

Candidate keys

MOTORBIKE(Province, Digits, Alphabets, Engine_number, Color, cc, Make, Model). The plate {Province, Digits, Alphabets} identifies a motorbike, and so does {Engine_number}. Both are minimal, so both are candidate keys. One is chosen as the primary key; the other is an alternate key. {Digits, Alphabets} alone is not a key: the same plate can be issued in two provinces.

Entity integrity and referential integrity

Entity integrity: no primary key value can be NULL, because the key is what identifies each tuple.

Referential integrity keeps tuples in two relations consistent. A set of attributes FK in R1 is a foreign key that references R2 if:

  1. FK has the same domain as the primary key PK of R2, and
  2. each FK value in a tuple t1 of r1(R1) either equals the PK value of some tuple t2 in r2(R2), in which case t1[FK] = t2[PK] and t1 refers to t2, or is NULL.

Five statements to be able to illustrate

  • Tuples in a relation do not have any particular order. Any order of the rows is the same relation.
  • NULL can have several meanings. The worksheet example inserts a student whose Plan is NULL: the value may be unknown, not applicable, or not yet available.
  • Keys are always superkeys. A superkey is any set of attributes that uniquely identifies a tuple. A candidate key is a minimal superkey: no proper subset of it still identifies a tuple uniquely.
  • A foreign-key value in a tuple can be NULL. A foreign key (FK) is a link between the attributes of one table and the primary key of another; FK values are allowed to be NULL.
  • The delete operation can violate only referential integrity, not key constraints nor entity integrity.

Joining on a primary key / foreign key

Joining Course (primary key Code) with Enrollment (foreign key CourseID) returns as many rows as there are foreign-key values in the field being joined: eight Enrollment rows give eight result rows.

In one lineDDL is the part of SQL that builds the empty tables and writes the rules the data must follow.

A table with rules

CREATE TABLE Member (
    MemberID INT PRIMARY KEY,          -- the official ID
    Name     VARCHAR(50) NOT NULL,     -- must be filled in
    Phone    VARCHAR(15) UNIQUE,       -- no two members share a phone
    Age      INT CHECK (Age >= 7),     -- any rule you can write as a condition
    Status   VARCHAR(10) DEFAULT 'active'   -- used when nothing is given
);

Every rule after a column is a constraint. Once it is written, the DBMS refuses any change that would break it. You do not have to remember to check; the database checks for you.

Linking two tables

CREATE TABLE Loan (
    LoanID   INT PRIMARY KEY,
    MemberID INT,
    FOREIGN KEY (MemberID) REFERENCES Member(MemberID)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

What happens to the loans when a member changes?

The words after ON DELETE and ON UPDATE are referential actions. They answer: "if the member row is deleted, or its ID changes, what should happen to the loan rows that point at it?"

ActionThink of it asResult for the loan rows
CASCADEFollow the parentDeleted too, or their MemberID changes to the new value
SET NULLUnlinkMemberID becomes NULL
SET DEFAULTRe-link to a fallbackMemberID becomes the column's DEFAULT value
RESTRICT / NO ACTIONRefuseThe delete or update of the member is rejected; nothing changes

If you write no action, MySQL uses NO ACTION, which in MySQL behaves the same as RESTRICT.

Choosing a type for each column

Every column gets a data type. The common ones: INT for whole numbers, DECIMAL(10,2) for money, VARCHAR(n) for text of varying length, CHAR(n) for codes that always have the same length, and DATE for dates written YYYY-MM-DD.

A rule can compare two columns

A CHECK at the end of CREATE TABLE is tested on every row and may compare columns of that row, for example "a loan cannot be returned before it was borrowed": CHECK (ReturnDate >= LoanDate).

Changing the data: INSERT, UPDATE, DELETE

  • INSERT adds a row: INSERT INTO Member VALUES (3, 'Ana', 'ana@mail.com');
  • UPDATE changes rows: UPDATE Member SET Email = 'new@mail.com' WHERE MemberID = 3;
  • DELETE removes rows: DELETE FROM Loan WHERE MemberID = 3;

The WHERE clause decides which rows are changed. Forget it, and UPDATE changes every row and DELETE empties the table.

Changing the table itself: ALTER and DROP

ALTER TABLE changes the structure of a table that already holds data: add a column, remove one, change a default, add or remove a constraint. DROP TABLE removes the whole table with its rows. DELETE empties a table; DROP makes it disappear.

Terminology

SQL says table, row and column for the relational terms relation, tuple and attribute. The main data definition command is CREATE.

Schema and catalog

  • SQL schema (a database): identified by a schema name, with an authorization identifier and descriptors for each element. Its elements are tables, constraints, views, domains and other constructs such as authorization grants.

Domains

A domain is a named type used in attribute definitions. Changing the domain changes every attribute that uses it, and the schema is easier to read: CREATE DOMAIN SSN_TYPE AS CHAR(9);. MySQL does not support CREATE DOMAIN.

Referential triggered actions

  • The default action on a foreign key violation is to reject the change.
  • A referential triggered action clause can be attached instead: SET NULL, CASCADE or SET DEFAULT, after ON DELETE and/or ON UPDATE.
  • SET NULL and SET DEFAULT do the same thing for ON DELETE and ON UPDATE: the referencing value becomes NULL or the default.
  • CASCADE suits "relationship" relations such as WORKS_ON, whose rows only make sense while both related rows exist.

INSERT, DELETE and UPDATE

These three commands change the data, not the structure. INSERT adds one or more tuples to a table. UPDATE and DELETE change or remove every tuple that satisfies the WHERE condition, so one statement can touch many rows.

INSERT: values in table order

List the table name and one value for every attribute, in the same order as the attributes in CREATE TABLE, including NULLs. Types and every constraint in the DDL (NOT NULL, keys, CHECK, foreign keys) are checked automatically.

DELETE

  • Removes tuples from one table; the WHERE clause selects which.
  • No WHERE clause deletes every row: DELETE FROM EMPLOYEE; leaves an empty table (the table itself remains).
  • Referential integrity is enforced. Rows in other tables are affected only through a referential action such as ON DELETE CASCADE.
  • The number of rows deleted is the number that satisfy the WHERE clause.
DELETE FROM EMPLOYEE
WHERE Dno = 5;

DROP

Removes a named schema element: a schema, table, domain or constraint, together with its data.

  • CASCADE: drop the element and everything that depends on it. DROP SCHEMA COMPANY CASCADE; removes the schema with all its tables, views and constraints.
  • RESTRICT: drop only if nothing depends on it (for a schema: only if it is empty); otherwise the DROP is not executed.
  • MySQL: DROP DATABASE company; (or DROP SCHEMA company;) always removes everything and takes no CASCADE / RESTRICT. DROP TABLE accepts the two words but ignores them; a table still referenced by a foreign key cannot be dropped.
  • DROP removes the table; DELETE removes rows and keeps the table.

Cardinality: how many?

6 Datalog and recursive queries
In one lineDatalog writes a query as rules of the form "this is true if all of that is true".

A rule has a head on the left and a body on the right of the arrow. The head is a result row; it is produced whenever every condition in the body can be matched.

late(n) <- Member(m, n, _) AND Loan(_, m, _, d) AND d < '2026-01-01'
  • Read it as: "n is in late if there is a member with ID m and name n, and a loan for member m with due date d, and d is before 1 January 2026."
  • Columns are matched by position, not by name. Member(m, n, _) means first column m, second column n.
  • _ means "there is a value here but I do not care what it is".
  • Using the same letter twice (m in Member and in Loan) means the values must be equal. That is how Datalog joins.

Safe rules

A rule is safe when every variable in the head, and every variable used in a NOT or in a comparison, also appears in a normal (non-negated) table in the body. If a variable is not tied to a real table, it could stand for any value at all, and the answer would be infinite.

Recursion

A rule may use its own name in its body. That lets you follow a chain of any length: a category, its parent, the parent's parent, and so on. SQL does the same with WITH RECURSIVE: a base case gives the starting rows, a recursive case adds the next step from the rows found so far, and it repeats until no new rows appear.

8 Heuristic query optimization
In one lineYou say what answer you want; the DBMS works out the cheapest order of steps to get it.

SQL is declarative: it describes the result, not the method. The same question can be computed in many orders, and some orders are thousands of times slower. The part of the DBMS that picks the order is the query optimizer.

Query trees

A query can be drawn as a tree. The tables are the leaves at the bottom, each operation (σ, π, ⋈, ×) is a node, and data flows upward to the answer at the top. Rewriting the tree changes the steps without changing the answer.

The rules of thumb (heuristics)

  1. Split a filter with many ANDs into separate small filters, so each can move on its own.
  2. Filter early: move each filter down the tree to sit right above the table it tests. Fewer rows go up.
  3. Join, do not pair everything: a Cartesian product followed by a matching condition is replaced by a join.
  4. Carry only what you need: keep just the columns used later (join keys and the output) as low as possible.

Why it matters

Pair 1,000 members with 50,000 loans and you get 50 million combinations before filtering. Filter the members to the 20 you want first, then join, and the work is tiny. Same answer, very different cost.

Details

A query is first written as a query tree: Cartesian products of the base relations at the bottom, one big selection of the whole WHERE clause above them, and the projection at the top. Heuristic optimization rewrites that tree into an equivalent one that is cheaper to execute.

The four steps

  1. Cascade selection — split the single conjunctive σ into one σ per condition.
  2. Move selection down — push each σ as far down the tree as possible, next to the relation it restricts (e.g. σProdType = 'Widget' directly over Product, σDate.Month = July directly over Invoice).
  3. Cartesian product with select becomes join — a × followed by a σ on a join condition is replaced by ⋈ with that condition.
  4. Projection push-down — add π nodes low in the tree so that only the attributes needed later (join keys and output columns) travel upward; e.g. πInvID, CustID over Invoice, πID, Type over Customer.

9 Transactions, commit and rollback
In one lineA transaction is a group of changes that must all happen, or none of them.

Moving 100 from account A to account B is two changes: take 100 from A, add 100 to B. If the system crashes between them, money disappears. Wrapping both in a transaction makes them one unit.

START TRANSACTION;
UPDATE Account SET Balance = Balance - 100 WHERE ID = 'A';
UPDATE Account SET Balance = Balance + 100 WHERE ID = 'B';
COMMIT;          -- make both changes permanent
-- or ROLLBACK;  -- undo both as if nothing happened

Two people at once

  • Inside your transaction you see your own changes straight away, even before COMMIT.
  • Other sessions do not see them until you COMMIT. They keep seeing the last saved value.
  • While you are changing a row you hold a lock on it. Anyone else who tries to change that same row has to wait until you COMMIT or ROLLBACK.
  • If a transaction is never finished, the DBMS normally rolls it back (for example when the connection closes).

Details

The lab runs two sessions (connections A and B) against bank accounts 10001–10003 and asks what each session sees after each numbered query.

  • A session sees its own uncommitted changes inside the same transaction: after A debits 100, A reads the decreased balance.
  • Another session does not see uncommitted changes (default isolation behaviour): B still reads the original balance.
  • While A holds a lock on the row, B's withdrawal and transfer cannot complete; they wait on A's uncommitted transaction.
  • After A executes COMMIT, the change is permanent and B's transfer completes.
  • After A executes ROLLBACK, all of A's changes are discarded (account 10003 is back to 1000).
  • A transaction that is begun and neither committed nor rolled back is, in most DBMSs, rolled back automatically; until then other sessions do not see its changes.

In one lineEvery account gets only the permissions it needs, given with GRANT and taken back with REVOKE.

A database is shared, so it must decide who can read and who can change. In MySQL an account is a user name plus the host it connects from: 'ana'@'localhost' is a different account from 'ana'@'%', where % means any host.

Roles: permissions in a bundle

Instead of granting the same five privileges to twenty librarians one by one, create a role, grant the privileges to the role once, and grant the role to each person. Change the role and everyone who holds it changes too.

CREATE ROLE 'librarian';
GRANT SELECT, INSERT, UPDATE ON library.* TO 'librarian';
GRANT 'librarian' TO 'ana'@'localhost', 'ben'@'localhost';

In MySQL 8, a granted role is not switched on automatically: the user runs SET ROLE, or an administrator sets it with SET DEFAULT ROLE.

Least privilege

Give each account the smallest set of permissions, from the narrowest set of hosts, that still lets it do its job. If it is ever misused, the damage is limited.

2 School database: DDL practice

Six CREATE statements for a kindergarten system. Each column type and each constraint comes from a sentence in the requirements, so read the requirements first and mark every rule word: unique, optional, must, only, between, linked to, automatically.

Requirements for the Kindergarten School System

Our goal is to create a system that accurately tracks our students, their contacts, and our staff. For every Student, we must capture their unique ID, full name, and optional nickname, with a strict rule that their recorded age must fall exactly between 3 and 5 years old. Each contact (Parent/Guardian) must also be uniquely identifiable and linked to their specific student, and we need to validate that the recorded relationship is only 'Mother,' 'Father,' or 'Other.' To avoid missing information, if a phone number isn't supplied for a contact, it should automatically be marked as 'N/A.' Turning to our physical resources, every classroom must have a unique identifier and a unique name. For staff, every employee must be uniquely identified, and we must enforce a business rule that all staff are adults, meaning their age must be strictly greater than 18. Finally, we must link a student to a specific classroom and an assigned staff member (teacher). This link must be complete, meaning a student and a classroom must always be specified. Most importantly, if an assigned teacher leaves the school and their staff record is deleted, the corresponding assignment must be protected from deletion. Instead, the staff identifier on the assignment record must automatically default to Staff ID 1, which is reserved for our director, ensuring continuous data integrity.

1.1) Explain the meaning of this constraint technically, e.g. if there is any update at … then … will happen.


1.2) Modify the constraint so that (1) when a supervisor resigns, the supervisees have no supervisor, and (2) when a new employee is admitted, an HR staff member is assigned as supervisor automatically. You may assume codes, names or other data.

    
Model answer
1.1 DEPTMGRFK makes super_ssn in EMPLOYEE a foreign key that references Ssn in the same table (a self-referencing foreign key for the supervision relationship). Every non-NULL super_ssn must equal the Ssn of an existing employee.


    

  • ON DELETE SET DEFAULT: if a supervisor's tuple is deleted from EMPLOYEE, the super_ssn of every employee he or she supervised is set to the default value of super_ssn. For example, deleting Franklin Wong (Ssn 333445555) changes super_ssn of Smith, Narayan and English from 333445555 to the default. The default must itself be an existing Ssn, otherwise the delete is rejected.
    • 

  • ON UPDATE CASCADE: if a supervisor's Ssn is changed, the new value is copied to the super_ssn of every supervisee. For example, changing Wong's Ssn from 333445555 to 333445599 changes super_ssn of Smith, Narayan and English to 333445599.
    • 



1.2 Assume the HR officer has Ssn 111111111 and already exists in EMPLOYEE.
ALTER TABLE EMPLOYEE
  ALTER super_ssn SET DEFAULT '111111111';      -- (2) new employees get the HR supervisor

ALTER TABLE EMPLOYEE DROP FOREIGN KEY DEPTMGRFK;
ALTER TABLE EMPLOYEE
  ADD CONSTRAINT DEPTMGRFK FOREIGN KEY (super_ssn) REFERENCES EMPLOYEE(Ssn)
  ON DELETE SET NULL                             -- (1) supervisees are left with no supervisor
  ON UPDATE CASCADE;

    
Explanation
    

  1. Read the clause from left to right. FOREIGN KEY (super_ssn) is the child column; REFERENCES EMPLOYEE(Ssn) is the parent key. Both are in EMPLOYEE, so one employee row points at another.
    2. 

  2. Each referential action answers one event on the parent row. ON DELETE says what happens to the children when the parent row disappears; ON UPDATE says what happens when the parent key value changes. A good answer names the event, the rows affected and the new value, using real tuples.
    3. 

  3. Requirement (1), "no supervisor", means the child value becomes NULL, so the delete action changes from SET DEFAULT to SET NULL. super_ssn must therefore allow NULL (it is not part of the primary key, so entity integrity does not apply).
    4. 

  4. Requirement (2) is about INSERT, not about the foreign key actions. The HR employee must exist first, or the foreign key rejects the insert.
    5. 

  5. Keep what was not asked to change. ON UPDATE CASCADE stays.
    6. 

  6. Name check. The constraint is named DEPTMGRFK, but it is the supervisor key, not the department manager key; the name does not change its meaning.
    7.

Q5 · 10 Why these rules are not safe


Explain why the following rules are not safe.
1) S(x) <- R(y)
2) S(x) <- R(y) AND NOT R(x)
3) S(x) <- R(y) AND x < y

    
Model answer
A rule is safe only if every variable that appears in the head, in a negated subgoal or in an arithmetic comparison also appears in at least one positive (non-negated) relational subgoal of the body. Otherwise the variable is not limited to values stored in the database, and the answer can be infinite.


    

  1. S(x) <- R(y): x appears in the head but in no relational subgoal; only y is bound by R. x can therefore be any value, so S is infinite whenever R is not empty.
    2. 

  2. S(x) <- R(y) AND NOT R(x): x appears only in the head and in the negated subgoal NOT R(x). Negation does not bind a variable: every value that is not in R qualifies, and there are infinitely many such values.
    3. 

  3. S(x) <- R(y) AND x < y: x appears only in the head and in the comparison x < y. For any y in R there are infinitely many values smaller than y.
    4. 


    
Explanation
    

  1. State the rule of safety first; each part is then one application of it.
    2. 

  2. Check variable by variable. For every variable in the head, in a NOT, or in a comparison, ask: is it inside a positive relation in the body? If not, the rule is unsafe.
    3. 

  3. Use a tiny instance to prove it. With R = {1, 5}: rule 1 returns every possible value; rule 2 returns every value except 1 and 5; rule 3 returns every value less than 5 (…, 2, 3, 4, including negatives and fractions).
    4. 

  4. How to fix (shows understanding): bind x in a positive subgoal, for example S(x) <- R(x), S(x) <- T(x) AND NOT R(x), S(x) <- R(x) AND R(y) AND x < y.
